# review-stepwise

## レビュー姿勢

* 対象に問題があるという前提で臨む
* 対象に付随する説明を鵜呑みにせず、対象そのものの内容を確認してから判断する
* 疑わしい点でも、根拠を確認できないものは指摘として提示しない

## ワークフロー

指摘は未処理・解決済み・却下・保留のいずれかのステータスを持つ。

1. レビュー対象を確認（ファイルパス、Globパターン、ブランチ差分など）
2. 指摘を重要度順（Critical → Major → Minor）に内部的に整理する（ユーザーには提示しない）
3. 指摘がなければその旨を伝えて終了
4. 現在の重要度グループの未処理の指摘を、見出しで区切ってまとめて提示する
5. ユーザーの判断・指示を待ち、応答を終える
6. 修正の指示があった指摘には対応し、「却下」と指示された指摘は却下として扱う
7. 対応の影響で他の未処理の指摘の内容が変わった場合、その指摘のみ内部的に再評価する
8. 再評価した指摘は、対応が必要な場合は保留、不要になった場合は解決済みとして扱う
9. 判断・指示がなかった指摘、および「保留」と指示された指摘は保留として扱い、解決済み・却下のいずれとしても扱わない
10. 現在のグループに保留が残っていれば、その保留中の指摘のみ再度提示する（ステップ4へ）
11. 現在のグループの全指摘が解決済み・却下になったら、次の重要度グループへ進む（ステップ4へ）
12. すべての重要度グループが完了したら終了

## 指摘の提示形式

```
# 重要度グループ名

## 指摘1: ファイルパス:行番号 — タイトル

理由と修正方針の両方を3行程度で説明する

## 指摘2: ファイルパス:行番号 — タイトル

理由と修正方針の両方を3行程度で説明する
```

## 重要度レベル

* Critical: セキュリティ上の問題、致命的なバグ、実装エラー
* Major: アーキテクチャ・デザイン上の改善、パフォーマンス問題、保守性の低下
* Minor: コードスタイルの統一、命名改善、ドキュメントの明確化

## 評価基準

* コードレビュー: write-code スキルの基準で評価する
* 文章レビュー: write-prose スキルの基準で評価する
* 修正の必要がない指摘には言及しない
